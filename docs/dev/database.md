# PostgreSQL setup and schema

The Compose database service prepares PostgreSQL infrastructure for later SQL integration. The current API still reads the existing Parquet files from `api/data`; these tables start empty, and this setup does not import Parquet data or change API queries.

## Create credentials and start the services

From the repository root, create `.env` once and start the stack:

```sh
./scripts/setup-env
docker compose up --build -d
docker compose ps
```

`scripts/setup-env` resolves the repository root from its own path, generates independent 256-bit hexadecimal passwords with OpenSSL, writes the file with owner-only permissions, and refuses to replace an existing `.env`. Keep `.env` private. `.env.example` contains only public defaults and placeholders.

Compose waits for the database healthcheck before starting the API. PostgreSQL is ready when `docker compose ps` shows the `db` service as healthy. The application connects inside Compose to `db:5432`. From the host, the database binds only to loopback at `127.0.0.1:${PGPORT:-5433}`; change `PGPORT` in `.env` if that port is already in use. Container-to-container connections always use port `5432`, regardless of the host port.

## Environment variables and roles

| Variable            | Purpose                                                                       | Example default                  |
| ------------------- | ----------------------------------------------------------------------------- | -------------------------------- |
| `POSTGRES_USER`     | Database administrator used by the official image during first initialization | `repoexplorer_admin`             |
| `POSTGRES_PASSWORD` | Administrator password                                                        | Generated by `scripts/setup-env` |
| `PGDATABASE`        | Database name and Compose-created initial database                            | `repoexplorer`                   |
| `PGUSER`            | Restricted application role                                                   | `repoexplorer_app`               |
| `PGPASSWORD`        | Application role password                                                     | Generated by `scripts/setup-env` |
| `PGPORT`            | Optional host port bound to loopback                                          | `5433`                           |

The administrator owns database initialization and schema setup. The application role has `CONNECT`, `TEMPORARY`, schema `USAGE`, and table `SELECT`, `INSERT`, `UPDATE`, and `DELETE` privileges. It is configured without superuser, database creation, or role creation privileges. Default privileges cover tables and sequences later created by the administrator in `public`.

For a host connection, use a local `psql` client and enter the application password at its prompt:

```sh
set -a
. ./.env
set +a
psql -h 127.0.0.1 -p "${PGPORT:-5433}" -U "$PGUSER" -d "$PGDATABASE"
```

## Initialization and persistence

`db.Dockerfile` uses the official `postgres:17-alpine` image. The entrypoint uses `POSTGRES_DB` to create `PGDATABASE` on the first initialization of the named `db-data` volume, then runs these files in order:

1. `scripts/db/setup.sql` creates or updates the restricted application role, grants access to the database and `public` schema, and sets default privileges.
2. `scripts/db/schema.sql` creates `repositories`, `organizations`, and `security`, applies the reusable `repository-scraping.sql` table/grant script, then grants table access to the application role. The Docker image copies the staging SQL files beside the schema file so its `\ir` include also works during initialization.

The Compose volume keeps database contents across container recreation and restart. Initialization files run automatically only when PostgreSQL finds an empty data directory. Changing `POSTGRES_USER`, `POSTGRES_PASSWORD`, or `PGDATABASE` in `.env` does not rename the existing administrator or change its password/database inside a volume that was already initialized.

### Safe bootstrap rerun

Rerun the SQL setup as the current database administrator to synchronize the application password and reapply grants. The command below runs inside the database container, uses the administrator for the connection, and passes application credentials separately to the scripts:

```sh
docker compose exec -T db sh -eu -c '
    application_user="$PGUSER"
    application_password="$PGPASSWORD"
    PGUSER="$POSTGRES_USER" PGPASSWORD="$POSTGRES_PASSWORD" \
        APPLICATION_USER="$application_user" APPLICATION_PASSWORD="$application_password" \
        psql -h 127.0.0.1 -U "$POSTGRES_USER" -d "$PGDATABASE" \
            -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/010-setup.sql
    PGUSER="$POSTGRES_USER" PGPASSWORD="$POSTGRES_PASSWORD" \
        APPLICATION_USER="$application_user" \
        psql -h 127.0.0.1 -U "$POSTGRES_USER" -d "$PGDATABASE" \
            -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/020-schema.sql
'
```

Bootstrap reruns are safe for the unchanged schema and preserve table data. `CREATE TABLE IF NOT EXISTS` does not migrate an existing table when columns or types change. Apply schema changes through an explicit migration before deploying code that depends on them.

### Change credentials on an existing volume

The official image does not rotate stored credentials from changed environment variables. Connect to the running database with its current administrator credentials, then use `\password repoexplorer_admin` and `\password repoexplorer_app` in `psql` to set the new passwords interactively. Update the matching values in `.env` and recreate the affected containers. The application role change can also be applied by the safe bootstrap rerun above after the Compose environment contains the new application password. Keep the old administrator password available until the role change succeeds.

### Destructive reset

**This removes all database data in the current Compose project's volume. Do not run it against a database you need to keep.** For a deliberate local reset only:

```sh
docker compose down --volumes
docker compose up --build -d
```

## Dataset snapshot and field mapping

The tables represent current snapshots. `repositories`, `organizations`, and `security` remain the dashboard datasets; `repository_scraping` is a raw collection staging table and does not change dashboard reads. Historical versions and ingestion are outside this setup. There are no foreign keys across datasets: repositories and security checks are collected independently, and repository URLs can repeat across universities.

The primary keys reflect the available fixtures: `(id, university)` for repositories and repository scraping, `(login, university)` for organizations, and `html_url` for security. Repository IDs repeat across universities, so `id` alone is not a key. The uniqueness observations do not guarantee the full upstream data; check full data before changing these keys or adding other uniqueness constraints. No full Parquet data files were present locally when this schema was prepared.

SQL columns use `snake_case`; each mapping below names its source field from [`appData.ts`](../../api/src/types/appData.ts). `YES` in the nullable column means SQL `NULL` is allowed. Nullability preserves the source type declarations and observed nulls, including nullable organization `name` and repository `busFactor` despite their non-null TypeScript declarations.

### `public.repository_scraping` field mapping

This staging table mirrors every `public.repositories` field and adds `scraped_at`. Its SQL names and types follow the `repositories` mapping above. It keeps required identity and measured counts non-null, while unavailable enrichment and downstream analysis columns are nullable. The scraper never writes to `public.repositories`.

| Staging field                                                                                         | GitHub source or rule                                                      | Stored meaning                                                                                                                                                                                                                        |
| ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `university`                                                                                          | Configuration `key`                                                        | Stable dataset identity. Configure it as the same full university name used by the existing repository dataset when rows are intended to align.                                                                                       |
| `id`                                                                                                  | Canonical repository `id`                                                  | Must be a positive safe JavaScript integer before database binding.                                                                                                                                                                   |
| `full_name`, `owner`, `html_url`, `description`                                                       | Canonical repository `full_name`, `owner.login`, `html_url`, `description` | Optional text fields become SQL `NULL` when GitHub returns `null`.                                                                                                                                                                    |
| `license`                                                                                             | Repository `license.spdx_id`                                               | Lowercase SPDX identifier; SQL `NULL` when the API reports no license; `other` when a license exists but has no usable SPDX identifier or reports `NOASSERTION`. Sample values include `mit`, `bsd-3-clause`, `gpl-3.0`, and `other`. |
| `language`                                                                                            | Repository `language`                                                      | SQL `NULL` when GitHub reports no primary language.                                                                                                                                                                                   |
| `fork`                                                                                                | Repository `fork`                                                          | Boolean encoded as the existing dataset's integer values: `1` or `0`.                                                                                                                                                                 |
| `created_at`, `updated_at`, `pushed_at`                                                               | Canonical repository timestamps                                            | Converted to UTC ISO timestamps before PostgreSQL stores them; `pushed_at` may be `NULL`.                                                                                                                                             |
| `homepage`                                                                                            | Repository `homepage`                                                      | SQL `NULL` when unset.                                                                                                                                                                                                                |
| `size`, `stargazers_count`, `watchers_count`, `forks_count`, `open_issues_count`, `subscribers_count` | Canonical repository count fields                                          | Validated non-negative safe integers. A measured `0` stays zero. `watchers` duplicates `watchers_count` to preserve the final repository shape.                                                                                       |
| `readme`                                                                                              | Repository README endpoint                                                 | Raw README text; a documented missing-resource `404` becomes SQL `NULL`. Other failures abort that university before writing.                                                                                                         |
| `organization`                                                                                        | Canonical repository `owner.type`                                          | The existing sample uses text `"1"` for organization-owned repositories and `NULL` otherwise. The scraper preserves that legacy marker.                                                                                               |
| `release_downloads`                                                                                   | All pages of public releases and each release asset's `download_count`     | Sum of measured counts; no releases or assets gives `0`. Missing or malformed counts fail the university scrape.                                                                                                                      |
| `contributors`                                                                                        | All pages from the contributors endpoint                                   | JSON array of unique contributor logins stored as `TEXT` (for example, `["alice","bob"]`); the endpoint's default excludes anonymous contributors. This is valid JSON, unlike legacy Python-style list text in some sample rows.      |
| `contributor_count`                                                                                   | Number of unique returned contributor logins                               | A measured zero is stored as `0`.                                                                                                                                                                                                     |
| `code_of_conduct_file`, `contributing`, `security_policy`, `pull_request_template`                    | Community profile content URLs or standard `SECURITY.md` locations         | Raw file contents. Missing optional files become SQL `NULL`; unexpected API errors fail the university.                                                                                                                               |
| `issue_templates`                                                                                     | Community profile issue-template content URL                               | One file is raw text. A template directory is JSON text containing `{path, content}` entries. No detected templates becomes SQL `NULL`.                                                                                               |
| `bus_factor`, `affiliation_prediction_gpt5_mini`, `type_prediction_gpt5_mini`                         | Downstream analysis                                                        | Inserted as SQL `NULL`; conflict updates preserve values already written by downstream analysis.                                                                                                                                      |

The implementation is in `find/src/enrichRepository.ts`; the checked-in SQL column order and keys are verified by `scripts/db/verify.sh`.

### Add the staging table to an existing volume

Fresh volumes create `repository_scraping` through `schema.sql`. For an existing volume, apply the repeatable table/grant script as the database administrator. It creates only the staging table and grants its CRUD privileges to the configured application role; it does not alter or truncate the three existing datasets:

```sh
docker compose exec -T db sh -eu -c '
    application_user="$PGUSER"
    PGUSER="$POSTGRES_USER" PGPASSWORD="$POSTGRES_PASSWORD" \
        APPLICATION_USER="$application_user" \
        psql -h 127.0.0.1 -U "$POSTGRES_USER" -d "$PGDATABASE" \
            -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/repository-scraping.sql
'
```

The script can be applied repeatedly. Keep the database container image in sync with the repository so the migration files are present. The scraper does not create schema and requires the restricted application credentials.
